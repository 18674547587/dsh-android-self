# dsh 安卓自建版：退出码 159 根因与修复

- 日期：2026-11-07
- 项目：`/srv/workspace/dsh-android-self`（GitHub: 18674547587/dsh-android-self）
- 构建：CI run #19（全部步骤成功，含冒烟测试）
- 产物：Release `build-19` → `app-release.apk`（298.7 MiB）

## 一、现象

手机（Android 10）上 App 状态栏显示「已退出 (159)」，端口 3080 永远等不到。

## 二、定位过程

`159 = 128 + 31 = SIGSYS`。Java 的 `Process.exitValue()` 对被信号杀死的进程返回 128+N，
所以这不是 dsh 返回的业务错误码，而是进程被 seccomp 杀掉了。

在 VPS（同为 Ubuntu 24.04 / glibc 2.39）上用自写的 seccomp 工具做单变量复现：

| 被禁的系统调用 | 跑 `node -e 'console.log("alive")'` |
|---|---|
| `clone3` (x86_64/arm64 都是 435) | **exit=159，无任何输出** |
| `rseq` (arm64=293, x86_64=334) | **exit=159，无任何输出** |
| `close_range` (436) / `openat2` (437) / `faccessat2` (439) / `pidfd_open` (434) | 正常，exit=0 |

把这两个改成返回 `ENOSYS` 而不是 KILL 之后：node、4 个 `worker_threads`、bash、git、
ssh、python3、npm、http 服务全部正常。

## 三、根因

Android 的 seccomp 是**白名单制**，未命中的 syscall 默认动作是 `KILL_PROCESS`，
而白名单是照着该版本内核的 syscall 表生成的：

- `clone3` 要 Linux 5.3（2019-09）才有；
- `rseq` 要 Linux 4.18。

Android 10 的内核是 4.14/4.19 时代，两个号都不在名单里。

Ubuntu 24.04 的 glibc 2.39 偏偏两样都用：

- `rseq` 在程序**启动阶段**就注册（所以死得最早）；
- `clone3` 在 `pthread_create` 里**先试**，只有拿到 `ENOSYS` 才回退到 `clone`。

于是 rootfs 里所有 glibc 程序都活不过初始化。另外 **proot 自己是 glibc 静态二进制**，
同样被 `rseq` 杀掉 —— 所以那行 `code=159` 甚至可能不是 node 的，而是 proot 自己的。

## 四、修复（三层，缺一不可）

| 层 | 改动 | 解决谁 |
|---|---|---|
| proot 源码 | `scripts/patch-proot.py`：在 syscall-enter 阶段把 `clone3`/`rseq` 伪造成 `ENOSYS` | rootfs 里的程序 |
| App 环境变量 | `GLIBC_TUNABLES=glibc.pthread.rseq=0` | proot 自己 |
| App 环境变量 | `PROOT_NO_SECCOMP=1`（原有，但原因此前没写清） | 让上面那条能生效 |

第三条的原因：内核会把多个 seccomp filter **链起来取最严格结果**，Android 的
`KILL` 会先于 proot 加速器的 `TRACE` 生效。只有纯 ptrace 模式（`PTRACE_SYSCALL`）
下，proot 才有机会在 seccomp 检查**之前**改掉 syscall 号。

选择这个方案而不是降级发行版，是因为它保住了「Ubuntu 24.04 + 能长期 apt 装工具」
这个前提，rootfs 一行不用改。

## 五、验证

1. **VPS 单变量复现**（x86_64）：禁 clone3/rseq → 159；改成 ENOSYS → 全部正常。
2. **CI 冒烟测试**（arm64 runner，`scripts/smoke-proot.sh`）：给 runner 装一个
   「clone3/rseq 命中即 SIGSYS」的 filter，再让补丁版 proot 拉 rootfs 里的 node：

```

==> 探针 1：node 单线程
smoke: node ok v24.22.2
==> 探针 2：worker_threads（真正会走 pthread_create 的那条路）
smoke: 4 workers ok
==> 探针 3：bash + git
smoke: bash ok
git version 2.43.0
冒烟测试全部通过
```

3. 待真机验证：Android 10 上装 build-19 的 APK，看是否还能看到 159。

## 六、经验

- 见到 `128+31` 就想到 seccomp，不要往业务逻辑上找。
- Android 上「老内核 + 新 glibc」的组合会踩这个坑，和发行版新旧无关，和内核版本有关。
- 判断某个 syscall 是不是元凶，最快的办法不是翻源码，而是在普通 Linux 上写个
  单条 syscall 的 seccomp filter 去复现。
